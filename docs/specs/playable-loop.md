# Built-client multiplayer acceptance

`bun run test:browser` runs the existing development-browser suite, then provisions fresh native fixtures for a built Pages-style client. The second suite builds Vite in explicit test mode into ignored `test-results/pages-build`, serves those static assets under `/scrabble/`, and uses the real game API and authoritative WebTransport server. The normal production output in `dist` is separate.

The test creates a game from the shared board, opens the invite in two independent browser contexts, names both players, starts, and verifies two disjoint private seven-tile racks. The first player previews and commits AT; the next player previews and extends it to CAT. Every client must converge after each commit on the complete public projection, scores, remaining count, and turn. Rack checks establish two replacement identities after AT, one after CAT, and an unchanged other rack. Waiting phones have disabled rack, commit and pass controls. The active player then previews another tile, opens and cancels pass confirmation, and confirms a pass. Every client must converge on the next turn with unchanged committed board, scores, bag and rack identities, and no tentative preview. A native negative test submits an owned commit from the non-active player and proves canonical state stays unchanged.

A test-only WebTransport reader observes actual snapshot datagrams before forwarding the unchanged bytes to the built application. The existing wire reassembler and strict domain schema decode them. Every frame must target the expected recipient, and every shared-board frame must contain an empty private rack. Welcome/reconnect credentials travel on the reliable welcome stream and are not inspected. The observer is outside the application import graph and stores no credentials.

The native factory selects creation inputs whose actual seeded deals support AT and CAT in the deliberately small authored dictionary. No rack or seed key enters metadata, and no gameplay state or projection is replaced. A test helper supplies those creation inputs through the browser's request generator. Endpoint/API configuration is compiled through the same VITE settings used by release builds. Local certificate pinning is compiled only in explicit test mode; ordinary release builds use normal TLS trust. Production routing now honors configured endpoints for board creation and board refresh.

`bun scripts/test-browser.ts --pages` runs the built-client scenario alone. Full gate: `bun run check`; it includes both browser suites. Shared policy sourceRevision: `46d8793bb3034326561f876dcc67dbaa5aa1e432`.
