# Reconnect and resume

Phone and board identities are private capabilities owned by the native runtime. Their separate, route-bound `sessionStorage` capsules hold only identity, rotated reconnect token, and sequence watermark. A refresh reuses the capsule for the same canonical match; neither surface silently creates a new player or match when resume fails. The shared board keeps its empty private rack and public presentation role after reconnect.

Both surfaces enable bounded automatic reconnect in `BrowserMatch`. After a connection ends, an existing capability gets three retries, delayed by 500, 1500, and 3000 milliseconds. A connection that receives a valid authoritative snapshot resets the retry budget for a later interruption. An initial connection with no capability is not automatically admitted again. Explicit disconnect, page hide, effect cleanup, and close cancel the delay and active transport. Manual retry starts a new bounded attempt with the same identity. Protocol incompatibility stops immediately.

Welcome rotates and persists the capability before any control is enabled. The client then enters `synchronizing`, with a five-second deadline for its first complete snapshot. The phone validates the private recipient, canonical game, and installed rules. The board validates its public role and empty rack. Only after the snapshot callback accepts the fresh state does the connection become `connected`. Retained snapshots can remain visible while disconnected but cannot authorize a move or Start. Sequence reservation is persisted before delivery; reconnect never resets the command watermark or resubmits a possibly accepted turn action.

The editor keeps an in-memory tentative draft across an ordinary interruption. Its context compares game, player, phase/turn, rack, and board against the restored snapshot. An unchanged context retains the draft and resumes tentative previews. A changed context clears it. A pending action is released when the connection becomes unavailable, with a request to inspect the restored turn before submitting again. Refresh deliberately starts with a fresh draft; no private rack or draft is written to persistent storage.

After unsuccessful retries, `resume-failed` reports that the session could not be resumed and may have expired or been replaced. Attempts stop; the phone exposes explicit retry or explicit new-player reset, and the board exposes explicit reconnect. WebTransport does not expose a dependable HTTP denial reason to the browser, so the client does not claim that every failed handshake proves expiration. Invalid or expired capabilities cannot become a replacement identity through retries. The runtime fences old connection epochs, rotates tokens, bounds reconnect grace, and rejects expired credentials. Expiry retains a started game's committed tiles, rack ownership, scores, and turn; an expired player cannot reclaim or control that seat.

## Verification

The Chromium reconnect scenario closes real native QUIC connections below the application, then verifies automatic phone and board resume, identity and private rack preservation, tentative draft retention, a subsequent accepted commit, phone and board refresh, and no second match or extra roster seat. A syntactically valid unknown credential exercises real admission refusal and verifies four total attempts followed by a stable terminal state without fallback admission. Existing browser tests cover repeated refresh, sequence persistence, isolated phone identities, and scoped snapshots. Runtime integration tests fence the old epoch after token rotation, preserve replay/recovery authority, and reject expired started capabilities without changing retained gameplay or adding replay records.
